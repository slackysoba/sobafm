# ADR-0007: Bound catalog audio decoding before choosing a runtime tool

- **Status:** Proposed
- **Date:** 2026-10-07
- **Issue:** [#118](https://github.com/slackysoba/sobafm/issues/118), parent [#114](https://github.com/slackysoba/sobafm/issues/114)

## Context

M5 proposes catalog tracks beside Lyria RealTime. A track would have to become the mixer's 48 kHz stereo signed 16-bit little-endian PCM without delaying its 20 ms reads. [#116](https://github.com/slackysoba/sobafm/issues/116) has an accepted offline research tool, but no live relevance, format, duration or size results. Its measurement timebox has not started. This proposal does not approve a catalog, decoder, binary supplier, license exception or security change. It must remain a draft until the adoption gates below are resolved.

The [earlier feasibility investigation](https://github.com/slackysoba/sobafm/issues/118#issuecomment-6032402289) covers the three candidate libraries/tools. The additional [offline evidence](../decoder-feasibility.md) tests one pinned Windows FFmpeg build with generated tones. It establishes incremental conversion and several failure paths on that host; it is neither a three-platform qualification nor a test of Jamendo audio.

[ADR-0001](0001-build-on-python-discord-py-and-the-google-gen-ai-sdk.md) requires installation without a compiler and permissive dependencies. Both the inspected PyAV bundle and FFmpeg candidates introduce copyleft components. Their wrapper/build-script licenses do not license the bundled native code. [ADR-0004](0004-stream-lyria-realtime-through-buffered-decks.md) historically estimated up to three buffers during handover. Three nominal 60-second PCM payloads total 34,560,000 bytes; subtracting that from NFR-3's decimal 40 MB limit gives 5,440,000 bytes. This is historical nominal arithmetic, not demonstrated current worst-case headroom or an enforced runtime ceiling. Current producer admission does not enforce a three-buffer or aggregate PCM-byte ceiling, and Lyria's 60-second pause target can overshoot. A four-minute whole-track PCM decode needs approximately 46,080,000 bytes and exceeds the audio-buffer limit by itself.

## Requirements

1. [NFR-4, OPS-3 and OPS-4](../requirements.md): released, verified installation paths for Python 3.14 on Windows x86-64, Linux x86-64 and Linux ARM64, including the container, without a compiler on the operator's machine.
2. MP3 input, including 44.1 kHz mono/stereo, becomes exact 3,840-byte playback frames in the existing PCM format. Actual catalog formats must first be measured by #116; an unsupported format fails one track.
3. The [mixer contract](../architecture.md#threads-and-buffers) remains intact. HTTP, native decoding, pipe I/O, process waiting and cleanup never run in `Mixer.read()`. Native decode work never runs on the event loop.
4. NFR-3 applies to resident audio buffers for a playing server, including compressed input, PCM copies and decoder audio buffering. Whole-process working set/commit and image size are separate measurements, not substitutes for this accounting.
5. Malformed input, stalls, cancellation and decoder exit fail one track and release its resources. A thread cannot contain a native crash. A subprocess can contain ordinary child failures, but resource limits and pipe-only arguments are not a security sandbox.
6. An approved binary-specific license, corresponding-source, vulnerability, update and footprint plan must precede distribution. Existing permissive-license policy and scanner settings stay in force until the maintainer explicitly resolves the conflict.

## Options considered

| Option | Fit and operating burden | Unresolved adoption condition |
| --- | --- | --- |
| Platform FFmpeg package, separate process | Reuses the OS package manager on Linux; native decode stays out of Python. Additional Windows installation and child lifecycle handling are required. Distribution packages have larger dependency closures than the executable alone. | Debian's default build includes GPL components. Exact versions, licenses, source availability, Windows supply, image delta and update ownership require approval. |
| Pinned prebuilt FFmpeg, separate process | Independent of Python ABI; the evaluated Windows shared build streamed MP3 successfully. Provider metadata lists Linux x86-64 and ARM64 artifacts. | The tested build reports LGPL-3.0-or-later, contains many unrelated libraries, and unpacks to 191 MB. Exact source/dependency inventory, retained supply, all-platform execution and memory enforcement remain unqualified. |
| PyAV or miniaudio in the bot | Python-facing streaming APIs simplify conversion, but a worker thread leaves native faults in the bot. | PyAV 19.0.1 has the required wheels but the inspected Linux bundle is GPL-3.0-or-later and about 131 MB unpacked. Miniaudio 1.71 has no released Linux ARM64 wheel. Neither satisfies the native-crash boundary in this form. Running either in a child would need a separately evaluated proposal and would retain its packaging/license obligations. |

The earlier investigation supplies the version-specific sources for the last row; it is not repeated here. A managed decoding service would add a service decision, transfer audio off-host and impose new operating obligations without solving this local need. No new service is proposed.

## Decision

No runtime decoder is selected. The conditional recommendation is to qualify **incremental FFmpeg decoding in a supervised child process**, because it addresses the native-crash requirement using an existing tool. Neither the tested archive nor the distro package is an approved distribution choice. The maintainer must settle the policy/build questions and accept a finalized record before implementation issues become Ready.

The smallest proposed application surface is a bounded catalog track producer that owns one child, feeds encoded chunks, drains output/errors concurrently, and hands frames through the existing frame-source interface. HTTP remains with the catalog client. There is no whole-track PCM result, decoder URL fetch, decoder-owned download, shell command construction or generic media pipeline.

### Proposed boundaries

These are reviewable candidate limits, not production constants or accepted changes to ADR-0004. #116 must demonstrate their usefulness before acceptance. Raising a limit requires revisiting the total budget, rather than only changing an individual cap.

| Boundary | Candidate limit and enforcement | Failure behavior |
| --- | --- | --- |
| Encoded input | 16 MiB cumulative per track, counted before each write regardless of `Content-Length`; at most 16 KiB per write, followed by flow-control drain. Retained encoded queue at most 256 KiB per child. | Reject advertised oversize early; abort on actual overrun. Do not retain the entire download. |
| Decode duration | At most 900 seconds, or 43,200,000 stereo sample frames, counted from output bytes divided by four. Metadata cannot extend the cap. | Reject overlong metadata; output crossing the cap fails the track rather than silently truncating it. |
| PCM delivery | Catalog reads at most 3,840 bytes; assemble across arbitrary short reads. Proposed hard catalog-buffer limit of 60 seconds per deck and a new candidate aggregate PCM envelope of 34,560,000 bytes per server across every retained live, ended/retired spare, filling and incoming source in both modes. Neither limit is an existing runtime ceiling or a three-source rule; Lyria flow control requires the qualification below. | Backpressure the catalog producer when its reservation is full. `Mixer.read()` only pops ready frames or returns silence. Preserve current Lyria behavior pending qualification and any required material decision. |
| Parent audio memory | Allocate/reserve before retaining bytes. Candidate ceiling 38,000,000 bytes per server across PCM, encoded queues, HTTP buffers, pipe transports, assembler tails and copies. Reserve up to 256 KiB for each stdout/stderr/stdin transport independently; reject a configuration whose combined reservations exceed the ceiling. | Refuse an additional producer until resources are released. Queue length alone is insufficient; account for byte lengths and copies. |
| Native audio memory | An audited maximum native audio-buffer reservation must also fit below 40,000,000 bytes with the parent reservation. If it exceeds the remaining headroom, lower the proposed parent/PCM budget before acceptance. | An unknown bound blocks adoption. The scratch working-set observation does not establish a native audio-buffer bound. |
| Child process resources | Candidate 128 MiB per child and at most two children per server/four globally. Use a separate Linux cgroup with `memory.max` and `memory.swap.max=0`, or a Windows Job Object with process/job memory limits and kill-on-close, established before untrusted bytes enter the child. | A cap breach fails that child/track. A bot-wide container limit alone can kill the bot and does not meet the proposed containment boundary. |
| Diagnostics | Concurrent stderr draining; retain at most 4 KiB, with a separately bounded reader transport. Record a fixed error category and exit status, never raw native diagnostics or URLs in user output/logs. | A noisy child cannot fill an unbounded diagnostic result or block stdout. |
| Time | 15 seconds to first PCM; 15 seconds without input/output progress while work is expected, excluding intentional queue backpressure; absolute lifetime at most `2 * 900 + 30` seconds, including pauses. | Timeout fails one track. Each input/pipe operation remains cancellable; a pause never disables the absolute lifetime cap. |
| Stop/cancel | Stop feeding; cancel and join all feeder/reader/consumer tasks; terminate, wait up to one second, kill if needed, then wait up to one further second. Close stdin and drain/discard bounded pipe chunks to EOF during cleanup. Release reservations only after cleanup completes. | Do not start a replacement if the old child cannot be reaped. Report cleanup failure and retain its capacity reservation. A second cancellation must not interrupt the bounded cleanup owner. |

A count of open producers does not account for all retained audio. The [supplemental independent review](https://github.com/slackysoba/sobafm/pull/157#pullrequestreview-5449091514), following [the sibling proposal's finding](https://github.com/slackysoba/sobafm/pull/156#pullrequestreview-5448974590), reproduced four nonempty Lyria buffers: an ended live source with 8 seconds, an ended ready spare with 60 seconds, and two replacement producers with 2 seconds each. `Station._generate()` counts open producers; `Station._discard()` can preserve that spare while neither replacement is ready. The fixture's 72 seconds total 13,824,000 PCM bytes: it disproves a hard three-buffer assumption but does not demonstrate an NFR-3 overrun or establish worst-case headroom.

Qualification of the proposed shared byte envelope must count every retained live, spare, retired/ended, filling and incoming source, regardless of whether its producer is open or which mode owns it. Include Lyria receive overshoot and in-flight chunks/copies through rotation, plan replacement, recovery, voice pauses and both directions of mode transitions. A future byte envelope can admit four partially filled buffers; it does not impose an unconditional three-source ceiling. Coordinate the admission/accounting policy with Proposed ADR-0006 in [#156](https://github.com/slackysoba/sobafm/pull/156), preserving current Lyria generation/spare-retention behavior and its tests. If that behavior cannot fit the candidate envelope, revise the proposal or obtain a separately recorded material decision before adoption; do not silently drop a spare, restrict replacement generation or change NFR-3. The numeric envelope and native/transport reservations remain unqualified.

Asyncio's reader `limit` is a flow-control threshold, not an exact memory allocation ceiling: the experiment with a 16 KiB limit observed a 52,508-byte stdout reader buffer. Transport reservations must include overshoot and in-flight chunks and be qualified against the chosen Python/build/platform versions. A reservation policy that cannot bound its transports must fail qualification.

The platform resource mechanisms are proposals for evaluation, not claims that the experiment exercised them. [Linux cgroup documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html) and [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) describe different accounting and enforcement semantics. Qualification must prove launch/assignment ordering, cap breach and tree cleanup under the actual unprivileged source/container installations. No runtime privilege increase or silent fallback to an RSS polling guarantee is approved. The feasibility of that installation is an adoption gate.

### Input, output and process contract

Use an absolute verified executable and fixed argument array with `asyncio.create_subprocess_exec`; inherit only the OS environment needed to launch it. Neither credentials nor source URLs enter arguments or the child environment. Force `-f mp3`, whitelist `pipe`, select `-map 0:a:0`, suppress other stream types, and explicitly emit `pcm_s16le`, two channels and 48 kHz to `pipe:1`. The catalog client owns URL validation and HTTP completion. [`-max_alloc`](https://ffmpeg.org/ffmpeg.html) limits one native allocation, not total child memory; it cannot replace the supervisor limit. The evaluated command is in the evidence report.

A nonzero exit, broken pipe, sample cap, missing/unaligned output, timeout or incomplete HTTP transfer is a track error. Zero exit alone is insufficient: the synthetic truncation test emitted only 1.96 seconds of a 240-second track and exited zero. Require clean HTTP completion, verify declared length when available, and compare decoded duration with validated catalog duration using a proposed one-second allowance for rounded metadata and codec padding. Unknown/inconsistent duration remains a validation-policy gate for #116/#125; do not silently label a partial track complete.

At verified normal EOF, a tail aligned to four bytes may be zero-padded once to a 3,840-byte frame, charged to the byte/sample reservations. An incomplete stereo sample is an error. Encoder delay/padding caused both successful fixtures to end between playback-frame boundaries; reads must not be assumed frame-aligned. Pending per-track recovery policy belongs to #119/#125/#127; this draft does not redefine current station behavior.

[Python's subprocess documentation](https://docs.python.org/3.14/library/asyncio-subprocess.html) requires Windows Proactor support and warns that `communicate()` retains output in memory. Concurrent bounded readers and explicit task ownership are required instead. Successful child reaping alone does not prove parent pipe closure; the scratch harness initially exposed unclosed transports before its cleanup was corrected.

### Binary license, source and upkeep obligations

The build supplier's MIT scripts and a permissive Python wrapper do not override FFmpeg or linked-library licenses. FFmpeg's [released license inventory](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/LICENSE.md) distinguishes LGPL, GPL, version-3 and nonfree configurations. The evaluated executable's `-L` reports LGPL version 3 or later; `--enable-version3` is present, and `--enable-gpl`/`--enable-nonfree` are absent. That is not a complete external-library audit.

Before any binary enters a SobaFM image or download, the chosen-build record must contain:

1. Exact artifact/version/architecture hashes, supplier and upstream commit, complete configure line, patches, dependency versions/licenses and a reproducible build recipe. Inventory every redistributed DLL/static component; exclude nonfree builds. Preserve copyright, license and required attribution notices in the image and accompanying documentation.
2. Exact Corresponding Source for each covered component, including modifications and build/install scripts. For a GPLv3/LGPLv3 artifact, propose the GPLv3 section 6(d) route: equivalent source access alongside binary distribution, with a durable source archive and explicit image-digest-to-source mapping. A moving upstream source link, daily archive or source tag without dependency sources is insufficient. [GPLv3 sections 1, 4-6](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/COPYING.GPLv3) and the [LGPLv3 supplement](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/COPYING.LGPLv3) govern the obligations. If an LGPL-2.1 build is chosen, separately document compliance with [its sections 4-6](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/COPYING.LGPLv2.1).
3. For applicable LGPL combined works, notices plus an approved shared-library replacement/relinking mechanism or the required relinkable application material; provide installation information where the license requires it. FFmpeg's [legal checklist](https://ffmpeg.org/legal.html) is a useful additional linking checklist. A pipe boundary is a technical boundary; the maintainer must approve the legal assessment of the actual distribution. This proposal does not pronounce all aggregation/linking arrangements MIT-compatible.
4. A named binary-update owner, review at least monthly and on upstream security notices, native-component advisory review and a recorded response deadline for applicable fixes. Proposed deadline: triage within two working days; suspend catalog decoding when an applicable serious defect has no approved mitigation. Every update needs hash/source/license/SBOM refresh, platform/cancellation tests and footprint comparison. A Python lockfile scan alone does not inventory bundled native code; use the [FFmpeg security history](https://ffmpeg.org/security.html) and advisories for included libraries.

Source retention duration, release hosting, scanner coverage and the exact copyleft policy treatment must be approved before adoption. BtbN's [retention policy](https://github.com/BtbN/FFmpeg-Builds/blob/9acad4a9ef1583096af7836cc1e9c8cbcb4d3950/README.md) keeps ordinary daily builds only fourteen days, so the evaluated dated download is unsuitable as the sole durable supply/source record. No hosting commitment, allowlist change, waiver or redistributable package is created here.

## Consequences

The offline results justify further qualification of incremental decoding, not release readiness. Compressed bytes and PCM can be streamed with small measured parent queues, and child failures can be followed by a healthy decode. Additional binary installation, supervision and distribution upkeep remain real costs to operators and maintainers.

Before finalizing this record:

- **#116 operator/maintainer, coordinated by the primary:** obtain the gated live go/no-go plus actual formats, sample rates/channels, duration and mp31/mp32 sizes/completeness observations. The current optional HEAD-only probe cannot establish bitstream format or decodability; any audio measurement needs a separately authorized bounded in-memory method. Do not start its timebox from this synthetic work.
- **Maintainer on #118:** confirm mandatory native-crash/resource containment; choose distro GPL, pinned audited LGPL, or a different qualified route, and explicitly resolve ADR-0001's permissive-license requirement. This may require a superseding decision. Approve concrete caps and behavior for unknown/mismatched duration. Recommended next assessment is a minimal audited LGPL build; the large evaluated archive is only a control experiment, not that build.
- **Assigned build evaluator after that choice:** produce exact source/license/SBOM/update inventory; execute install/conversion/cancellation/cap-breach tests on all three targets; measure Linux image/layer delta and child/parent memory. Establish native audio-buffer bounds and source/container supervision feasibility. Neither Linux target has been executed by this work.
- **#119/#125 owners after acceptance:** implement the agreed budget/lifecycle policy and per-track EOF/recovery behavior. First qualify admission/accounting across all retained sources and Lyria receive overshoot with the #117/#120/#121 owners, preserving existing generation/spare behavior unless a material change is explicitly approved. Add regression tests for truncated input, arbitrary read splits, cancellation during backpressure, failed cleanup and overlapping sources, then qualify live crossfade/underrun behavior under the milestone's separately authorized test plan.

[Issue #118](https://github.com/slackysoba/sobafm/issues/118) remains Blocked and labeled `maintainer-approval`; #119-#132 remain gated. This record and its evidence do not close the decision. Accepted requirements, architecture, dependencies, container and security settings are unchanged.

## Revisit triggers

- #116 finds non-MP3 formats, durations/sizes outside the agreed caps or unacceptable relevance.
- A candidate's native audio memory or image footprint cannot meet the approved budget, or supervision cannot work on a supported installation.
- License/source obligations cannot be satisfied, the supplier removes retained artifacts, or an applicable parser vulnerability cannot be mitigated promptly.
- A permissively licensed candidate gains complete platform packaging and independently verified child-process containment with a smaller operating burden.
