# Architecture

The catalog selector, station and credit logic, PCM banks, decode producer, persisted settings, change cooldown, Discord adapter and generated playback are implemented. `python -m sobafm` connects them with a startup limit gate, and a Dockerfile and Compose service package the result. Historical images have run on Docker Desktop WSL2 amd64, including private catalog/Discord sessions and image checks. The [reviewed corrected L2 pass](https://github.com/slackysoba/sobafm/issues/3#issuecomment-6789773813) covers only a finite synthetic buffering workload on application `01e2226`, image `bd7d1aee`, with harness `37e2b8f`; [operations](operations.md) records its full source/image/target binding, earlier failed setup and remaining integration gaps. The Docker resource model is [accepted](decisions/0004-amd64-whole-service-adoption.md); current-main and release qualification remain incomplete. The piped-host experiment [#151](https://github.com/slackysoba/sobafm/issues/151) remains deferred and native arm64 remains on hold under [#60](https://github.com/slackysoba/sobafm/issues/60).

SobaFM has one station/player per server. Commands validate access and intent. A mode-specific interpreter produces a validated musical plan. Catalog selection or generated production prepares audio; the connected player settles what listeners actually hear. Settings and remembered channels persist in SQLite.

Listeners in one voice channel share that station's audio. The maintainer selected one bot identity and three simultaneous stations in [#166](https://github.com/slackysoba/sobafm/issues/166). Three exclusive two-slot reservations now cover catalog preparation, generated renewal and retained cleanup work. A fourth station is refused before interpretation; an idle voice connection reserves no station. [ADR 0012](decisions/0012-three-station-capacity.md) states the proposed changed limits, pending numeric acceptance and actual-image qualification. [#171](https://github.com/slackysoba/sobafm/issues/171) separately owns broad catalog access before deployment.

Catalog preparation happens ahead of playback: source admission, provenance, credits, curation and descriptors. The current prepared catalog contains 167 FMA recordings; runtime selection ranks admitted candidates and playback reads local files. Broad source-catalog search and on-demand audio retrieval are not implemented. Jamendo remains parked and ccMixter is not an enabled audio source.

## Implemented catalog boundary

`catalog.py` validates bounded prepared metadata and separate trusted admission reviews, and `eligible` returns the admitted recordings from every supplied partition. Reviews bind complete credits and access readiness to an immutable recording digest. Unreviewed, changed, unavailable or incomplete recordings remain rejected. No provider or model approval field is accepted in recording metadata. Each recording may carry `details`, source text such as tags, tempo and album kept as matching hints. They stay outside the digest, so enriching them leaves reviews valid.

`gemini_interactions.py` makes one bounded call to the Gemini Interactions API ([ADR 0006](decisions/0006-gemini-play-matching.md)). A `GeminiClient` holds the API key, the transport and the limit on calls in flight. Calls have `store` off, a response schema, a 10-second timeout, a 64,000-byte response limit and no retries. At most four run at once per client, and one client serves all servers: a request body is built only once its call holds a slot, and waiting for one counts toward the same 10 seconds. After `close` the transport refuses further calls, so a request arriving during shutdown can't open a new session. Failures raise `GeminiFailed` with a safe kind. Its `blocked` fact means Gemini says it blocked the call: a 400 whose `error.code` is one of the codes on the [safety settings](https://aistudio.google.com/docs/safety-settings#when-content-is-blocked) and [API errors](https://aistudio.google.com/docs/api-errors#generation-blocked-codes) pages, or a `failed` interaction recording such a code, a form the safety page documents for background calls. The kind doesn't change, and the code and message aren't kept or logged. Nothing documents a block in a 200 with no usable output: `incomplete` with empty text [means the tokens ran out](https://aistudio.google.com/docs/long-decode#background-status). Those pages give a 400 only for `safety`, `jailbreak`, `prohibited_content` and `blocklist`; the 400 is assumed for the other codes, and any other status isn't treated as a block. `AiohttpTransport` uses the `aiohttp` already in the lock, follows no redirects and creates its session on first use.

`gemini_match.py` turns a `/play` request into a list of recordings, with one such call per list ([ADR 0011](decisions/0011-program-refill.md)). `GeminiMatcher` owns the service's client and prepares a compact description of the admitted recordings once at startup, refusing one over 512,000 characters. A call sends the JSON-encoded request and the admitted recordings the program hasn't played: the first call uses the prepared description, and a later one renders the smaller list while it holds a slot, numbered afresh. With none left it makes no call and fails with `NO_RECORDINGS`. `parse_plan` rejects the whole output unless it is exactly the expected shape and names only distinct positions in the list sent, so the model can only choose an admitted, unplayed recording. The result is `Matched` (1 to 8 recordings, best first, each with a fit of exact, close or loose) or `Refused`, and failures raise `MatchFailed`, its name for `GeminiFailed`. The instruction asks for 8 and allows fewer only when fewer are listed, but a shorter list is accepted, because it only brings the next call sooner. `/play` doesn't read `blocked`: a block is an ordinary failure there, because every failure already leaves current music unchanged. Only the kind, outcome, count and duration are logged.

`catalog_import.py` converts bounded saved Jamendo tracks responses, ccMixter info responses and explicit FMA operator manifests into the same validated snapshot schema. Source-specific field maps preserve identity, credit evidence and unknowns. A separate report records malformed rows, missing requested IDs and bounded source coverage; conflicting duplicate identities are quarantined together. Outputs contain no media URLs or generated admission decisions. The importer's draft metadata still needs complete-kind/access evidence and separate credit review before selection admission. See [saved metadata imports](catalog-evaluation.md#saved-source-metadata-imports).

`catalog_prepare.py` and `media_check.py` apply the batch rule in [ADR 0007](decisions/0007-fma-dataset-batch-catalog.md) at ingestion. `catalog_prepare.py` decides which FMA dataset listings qualify and in what order, turns a listing into the importer's manifest form, marks validated recordings complete and available, and writes the media manifest and the reviews. `media_check.py` decodes a file through the real `DecodeProducer`, screens the decoded audio for long silence and sustained clipping without keeping it, and reads its ID3 tags. Neither makes a network request or uses a model, and the running service imports neither. The two scripts under `evaluations/catalog/` drive them: `fma_fetch.py` makes the requests, through one metered client with stop conditions, and `fma_build.py` runs the offline stages.

Partition completeness describes only the dated prepared subset. `catalog.py`, `catalog_import.py` and `catalog_prepare.py` perform no provider calls, audio access, state changes or Discord operations. See the [catalog contract](catalog-evaluation.md#current-selection-contract) and accepted decisions [0002](decisions/0002-prompt-catalog-selection.md) and [0006](decisions/0006-gemini-play-matching.md).

The audio callback consumes prepared PCM without blocking. Producers and cleanup retain explicit ownership across cancellation. Capacity admission includes retained work and cleanup debt. Prove the chosen Linux enforcement configuration before depending on it throughout the application.

## Generated-plan interpretation

`freestyle_plan.py` turns a `/freestyle` request into a validated generated plan with one call through `gemini_interactions.py`. Catalog matching and generated interpretation share the matcher's client and its four-call limit. In a generated-only configuration the interpreter owns the client.

`PlanInterpreter.interpret(request, current)` has three outcomes, each its own type:

- `Planned` holds a `GeneratedPlan`: a title of at most 60 characters, one to four distinct styles with weights from 0.1 to 1.0, each as long as a request at most, so a fallback plan's style stays valid if the model keeps it as context, and optional tempo (60 to 200 BPM), key (twelve scales), density and brightness (0 to 1), `mute_drums` and `wordless_vocals`. These follow [Lyria RealTime's guide](https://aistudio.google.com/docs/realtime-music-generation) and [API reference](https://aistudio.google.com/api-reference/live-music), checked on 2026-11-05. The plan uses plain values and no transport types. Lyria normalizes weights and doesn't take zero, so the plan's weight range is a positive part of what Lyria accepts.
- `PlanRefused` means the model judged the text unrelated to music, a prompt-injection attempt or disallowed, or Gemini blocked the call. Current music must not change.
- `PlanFallback` means interpretation failed some other way: a timeout, a provider or transport error that isn't a block, or output that isn't exactly the expected shape. The checked request becomes the only style, under a fixed title and with every control left to the generator. Its type is the flag for disclosure, and `failure` holds the safe kind.

Output naming the refuse outcome is a refusal whatever else it holds, and so is a provider block, because treating either as a failure would send text that was just declined to the generator. All the documented block codes count, including `language`, which says nothing about the content: a wrong refusal leaves the music playing, and a wrong fallback gives it up. Replies to a refusal therefore shouldn't assume the listener asked for something disallowed. Text failing `checked_request` raises `CatalogInputError` with no call or fallback, and cancellation propagates, so a fallback never starts music for a request nobody is waiting on.

Any other failed call has no verdict, so hostile text that also makes the call fail reaches Lyria as a direction, where it meets [Lyria's own safety filter](https://aistudio.google.com/docs/realtime-music-generation#limitations) and has no tools to reach. The same applies to an artist's name, which only a successful call can translate into musical characteristics. A relative request that fails sends only its own words: `faster` becomes the only style and the plan now playing is dropped, so the disclosure should say the request was used as written.

The prompt holds the fixed instruction, the JSON-encoded request and, for a relative request, `current`: the generated plan now playing, as JSON. The signature accepts nothing else, so no Discord identity can reach it and the API key stays in a request header. A catalog program can't be `current`, so switching modes starts a fresh interpretation. The instruction asks for descriptive characteristics in place of artist names and for no lyrics, and the plan has no field that could carry lyrics. Whether the model follows that instruction is a question for the [opt-in evaluation](../evaluations/gemini_matching/README.md), which hasn't been run. Only the kind, outcome, style count and duration are logged, never titles or styles, and a title must be escaped before it is shown.

The guide calls the model instrumental only and also documents a `VOCALIZATION` mode that adds vocalizations "as another instrument". It doesn't mention words, so whether `wordless_vocals` output stays wordless needs a live check. The guide also says a new `bpm` or scale takes effect only after a context reset, and each accepted generated plan starts a fresh session with its full config. Offline tests use local fakes and establish validation, failure handling and the request's contents. They don't establish that the live API accepts this schema or that plans sound like their requests.

## Implemented PCM boundary

`pcm.py` fixes the playback format in one place: stereo signed 16-bit at 48 kHz, 192,000 bytes per second and 3,840-byte 20 ms frames. `GLOBAL_PCM_BANKS` owns three `StationReservation` objects, each with two 2,304,000-byte banks, for 13,824,000 reserved PCM bytes ([ADR 0012](decisions/0012-three-station-capacity.md)). A guild reserves its pair before interpretation, without allocating PCM. It leases backing only when production starts. A reservation stays charged through pending requests, native/session settlement, bank views and voice frames, including after disconnect; a same-guild restart reuses it. Returned reservations reject stale allocations. Each bank retains the original cancellation timestamp and refuses release while a producer region or any view still exists. The pool's direct methods serve a single two-slot reservation for standalone producer tools within the same three-reservation budget.

Each bank is a single-producer, single-consumer ring. The producer borrows a contiguous free region (suitable for a pipe `readinto`), fills it outside the bank lock and commits the filled prefix. It must settle every borrow with `commit_write`, using `commit_write(0)` on error, even if it already released the region view. `write()` is a copying convenience. The voice callback's `read_frame()` takes the bank lock without waiting and copies at most one 3,840-byte frame. It returns `None` when no frame is available now (not ready, underrun or a brief contended operation) and `b""` once no frame will follow. `ready_now()` reads the monotonic readiness flag without the lock, so the callback can tell an underrun from a stream that is not yet ready. Frames are readable only after readiness: 1,152,000 buffered bytes (six seconds), or the producer's verified end of a shorter valid stream. A decoder's output length need not be a multiple of the frame. At the verified end, a stream that is a whole number of 4-byte stereo samples and holds at least one whole frame is valid PCM; its remainder, shorter than one frame, is not emitted, and audible drain follows the last whole frame. A length that is not a whole number of samples means truncated output and fails as `partial_final_frame`; a nonzero stream shorter than one whole frame has nothing to emit and fails as `empty_pcm`, as does an empty one. Partial bytes are never emitted or padded with silence.

Transfer completion and decoder completion are recorded by their owners. Valid PCM comes from the verified end-of-PCM check. Audible drain means every whole frame of an ended, admitted stream has been handed to the voice callback. Each fact is tracked separately and none implies another. The module has no Discord library, decoder process, station logic, threads or dependency. `wait_writable()` lets a producer wait for free space without polling; the voice callback's frame reads notify it and never block. The decode producer below supplies the first completion policy and cleanup owner; voice integration belongs to a later slice. The 3,840-byte frame copy returned to the callback, and the second one the volume gain makes from it, are application audio copy payload under the separate copy reservation; this module does not account for them. Offline tests do not qualify voice timing, Linux containment or useful fit.

## Implemented decode producer

`decode.py` is the first-slice producer for one admitted recording. A `DecodeInput` names the local file, its exact size and SHA-256, and a finite PCM output limit chosen by the caller; the limit is an overrun bound, not a duration oracle. One `DecodeProducer` owns the input file, one stock mpg123 child in its own process group, the child's stdin/stdout pipes, a feeder thread, a reader thread and one `GLOBAL_PCM_BANKS` lease. A caller that already holds a lease can pass that bank instead: the producer fills it at the same point in the launch, never acquires, keeps the bank's earlier first cancellation as its original clock, and leaves release of the lease to the caller.

Launch follows the [ADR 0004](decisions/0004-amd64-whole-service-adoption.md) premises. The decoder is started with `subprocess.Popen` (pipes, no PTY, stderr discarded, closed descriptors, a fixed minimal environment) before this producer leases PCM or starts a thread. `Popen` returns once exec has replaced the child's image, so a forked child image is gone before any input; any bank it could have inherited was already leased and charged. The reviewed per-decoder limits (core 0, stack 524,288, data 12,000,000 and address space 12,524,288 bytes) hold before the first input byte. `Popen` returns partway through exec, and the kernel ends exec by restoring the stack limit it pinned at the start, so a limit set from the parent can be lost. So the child sets the stack limit itself: `Popen` starts `/bin/sh -c 'ulimit -s 512 || exit 125; unset PWD; exec "$@"'` with the decoder's argv. The `exec` replaces the shell, so there is still one process in one group and no extra task, and the shell reads no input. Unsetting `PWD` keeps the decoder's environment exact, because dash would otherwise add it. Exec keeps the other three limits, so `prlimit` sets them after `Popen` returns and before the feeder starts. It sets the stack limit too, which reports one that can't be set as `decoder_limits` before any input. A launch with no stack limit skips the shell step. Exec resets the non-dumpable attribute of the main process, but the decoder inherits its `coredump_filter` of 0, so on a host that pipes dumps a decoder crash sends the handler no memory contents. The argv is the one the #44 evaluation established: stereo signed 16-bit at 48 kHz on stdout, input on stdin, `--no-resync`. A test pins it to that established value.

The feeder streams the file through a fixed 16,384-byte chunk, checking size and hash, and closes stdin only at exact verified EOF. A truncated, oversized, unreadable or mismatched input never gives the decoder end of input: stdin stays open until the child is reaped. The reader fills the bank through `reserve_write`/`commit_write` and waits on `wait_writable()` when the bank is full. Output beyond the limit is an overrun. Transfer completion, decoder completion (exit status zero without cancellation, because mpg123 also exits zero on SIGTERM) and valid PCM are recorded separately in the bank and the `DecodeReport`. The verified end of PCM is declared only after a complete transfer, exit status zero and no failure, so a nonzero exit after full output and an overrun fail. The bank then applies the length rule above: sample-aligned output ending inside a frame is valid and every whole frame stays readable after `finish()` returns, while output that is not a whole number of samples or holds no whole frame fails. Any failure stops the bank's stream. Consumers only read frames from the bank and stop a decode through `DecodeProducer.cancel()`, not by cancelling the bank directly.

`finish()` is the single cleanup owner. The original deadline is three seconds after the first of cancellation, a failure or the decoder's end of output; repeated cancellation does not reset it. Cancellation or failure sends SIGTERM to the group at once and SIGKILL two seconds in. Once the stream stops, the reader closes the decoder's stdout, so a decoder blocked writing to a full pipe gets EPIPE and acts on SIGTERM instead of waiting for SIGKILL. If the bank's owner stopped the stream before calling `cancel()`, the reader first adopts that cancellation, with the owner's original time, so the decoder's exit and any failed input write count as cancellation; a decoder that ends its output but does not exit within one second is a stalled failure. The leader's exit is observed through a pidfd, the group is swept with SIGKILL while the unreaped leader pins its ID, and then the leader is reaped. Threads are joined and descriptors closed only after that. If a feeder or reader thread cannot start, that is a `thread_start` failure, and only the threads that did start are owned and joined. Settlement after the deadline is an `expired` verdict that a later release never changes. `release()` returns the bank lease only after the process, threads and descriptors have actually settled, and only when the caller no longer needs the bank.

The input chunk is application audio/IPC copy payload under the separate copy reservation, which this module does not account for. Tests use small Python children in place of mpg123. They do not qualify native mpg123 behavior, the limits under the real image, or fit under the group limit, which is a later local step.

## Implemented station facts and credits

`station.py` keeps one server's desired program, prepared audio, claimed switch and heard source as separate facts in a single-owner `Station`. Each accepted request gets an increasing generation and reports the unheard program whose work the caller must cancel. Preparation results, failures and switch reports carry their program or claimed audio; anything for a superseded program is returned as stale and changes nothing. Catalog audio can be offered only after its credits render. Generated audio carries the validated plan and uses the stream’s six-second pre-roll. The player claims ready audio and then reports an actual switch or failure; only the switch changes the heard source. A failed, rejected or cancelled replacement reverts the desired program to the one still heard and leaves its credits unchanged. Stop ends the desired program, recording why when it ended without a command (an expired listener grace period); the heard source clears only when the player reports silence. A program carries the list of recordings that `/play` obtained, and continues: after its first track is heard, `continue_program` opens the next track's preparation, `refilled` replaces a list that has run out with validated recordings not in its history (`REJECTED` if none are new), `exhausted` records that none can follow (the program then ends when its heard track reports `drained`, with `ended` giving the reason until a new request or stop), and a failed next track keeps the program rather than reverting it. Each program has a bounded no-repeat history of every recording it prepared or tried, including credit-rejected ones; its size, 768, is the most recordings a valid snapshot can hold, so history is never cleared or evicted to repeat a track. Continuation facts are kept only for programs still desired, heard or holding audio, so a failed replacement restores the heard program's history and ending. `select_next(plan, history)` chooses each track: the best-ranked recording in the program's plan that its history doesn't hold. The module holds no audio, tasks, threads, persistence or clock, and records a generated plan and its fixed cutoff with the same switch and drain lifecycle.

`credits.py` renders a recording's existing `catalog.py` credit snapshot: title, creators, source backlink, license and every notice. Provider text has bidirectional controls stripped, other control and line/paragraph separators replaced by spaces, and Discord markdown, mention, emoji and autolink characters backslash-escaped. Links are rendered only after the catalog's credential-free HTTPS validation plus an RFC 3986 character check, inside angle brackets. Pages are filled continuously up to 1,968 UTF-16 code units plus a footer, within Discord's 2,000-unit message limit; credits needing more than 16 pages raise `CreditRejected`, and the station treats that as a rejected candidate rather than truncating notices. Each page states that mentions are disallowed and previews suppressed for the Discord layer. `CreditViews` retains at most 256 caller-bound views, each expiring a fixed time after opening (600 seconds by default, at most 900) under injected monotonic time; it expires old snapshots and evicts the oldest settled view when a new menu needs room. Wrong-caller, unknown/expired and out-of-range requests receive refusals without page content.

## Implemented Discord adapter

`discord_adapter.py` registers `/join`, `/play request:<text>` and `/freestyle request:<text>` (1 to 200 characters each), `/skip`, `/now`, `/stop`, `/leave` and `/settings [duration] [volume] [cooldown]` with an `InteractionBot` that requests exactly the Guilds and Voice States intents. Commands are registered for the server context only and also refuse a missing server at runtime. `/settings` is registered with or without a catalog. `/join`, `/leave` and `/settings` carry Manage Server as their default member permission, so administrators customize access through Discord command permissions rather than a second role system. `/play`, `/freestyle`, `/skip` and `/stop` require the caller to be in the bot's voice channel; `/stop` also accepts a caller with Manage Server from elsewhere. `/now` has no extra requirement. Without a joined voice connection, `/play`, `/freestyle`, `/skip` and `/stop` explain that a manager must use `/join`. `/now` answers at once; the other commands defer before any voice, selection or cleanup wait, all ephemerally and with mentions disabled. If the deferral of `/stop` or `/leave` fails, whether Discord rejects it or the request does not complete, the command still silences (and `/leave` disconnects), sends no follow-up and logs the command name, the interaction's age and Discord's status and code or else the exception type, never its token.

`/play` defers, then asks the injected `Matcher` for a plan. A refusal or `MatchFailed` changes nothing and says so. One request is matched at a time per server; another during that wait is refused without a call. A `/stop`, `/leave` or shutdown during the wait wins, so the plan is then dropped. Otherwise the plan becomes a new `station.py` program carrying the list, starting with the first recording whose credits render, and the reply states its fit using fixed wording and escaped catalog text. Later recordings may fit less well, and no reply discloses their fit. The adapter then claims the audio, leases a `pcm.py` bank from `GLOBAL_PCM_BANKS` and starts the injected `Producer` on the event loop. A refused lease reports a failed switch, leaving current audio heard. Only one unheard track is pending per server: a newer request displaces it, reports its switch as failed and joins its retirement (bounded by five seconds) before leasing again. Responses say the request is accepted and preparing, never that it is audible.

The voice player reads `StationOutput`, which wraps `StationSource` and applies the server's volume to each audio frame, as described under [settings and cooldown](#implemented-settings-and-cooldown). `StationSource` is the voice callback. It takes its lock without waiting. A catalog boundary copies a single frame. A generated crossfade reads both banks and mixes one output frame. It switches when the pending bank yields its first frame, which `pcm.py` allows only after readiness. Before that, and during an underrun, it returns a silent frame so the player keeps its timing; it never pads a partial final frame. Under the same non-blocking lock it counts, as plain integers on the track, the whole frames it handed to the voice player and the silence frames it returned while the track was current, or pending and ready (underruns, which include a frame skipped because the bank's lock was momentarily held). These are frames handed to the player, not packets confirmed delivered. Switch, failed, drained and retired reports go to the event loop with `call_soon_threadsafe`. Only the switched report changes the heard source, so `/now` keeps the heard title and full credits until then, across every track boundary, and states when a newer request is starting. `/now` sends a private status line followed by the first credit page. Multi-page credits carry a page selector. The adapter uses the original command ID from the private follow-up and verifies the listener before editing the message. One timer expires snapshots. A menu send keeps one of the 256 slots until the SDK settles, even after its snapshot expires. When all slots are delivering menus, the next listener gets a private retry reply. Shutdown revokes navigation, cancels outstanding sends and waits up to the original three-second deadline. A send still outstanding keeps its owner and a missed deadline remains a failure after release. Delivery errors log the operation and exception type. Credit messages and edits suppress mentions and previews. When nothing is current or pending, the source returns end of stream and the player stops; the next claim restarts it.

A pending track is either a cut, which switches at its first ready frame (a new program's first track, or `/skip`), or a continuation, which the callback reads only once the current track has drained: in the same callback that finds the current track's end it emits the continuation's first frame, so catalog tracks play successively with no fade, overlap, looping or editing. When a program's track is heard, the adapter starts one continuation task for the server, recording which program it serves. A task still running for a superseded program, for example one waiting for capacity, is not reused: the newly desired program gets its own task, and the old one stays owned until it exits through its stale check. Under the player lock and only if the program is still desired and has no next track, it first checks the program's list: with nothing left on it, it starts a [refill](#implemented-program-refill) and returns at once. Otherwise it checks the pool: a retiring track still holds its bank and is counted there, so the continuation never waits on retirements themselves, and a stuck retirement elsewhere does not delay it while a bank is free. With a free bank it takes the next recording from the program's list and history (at most three credit-rejected candidates per preparation), claims the audio and leases that bank. So at most the audible track and one prepared next track hold this station's two banks. Another server cannot consume either slot. Without a free bank the continuation waits, consuming no attempt, until a retirement settles, a callback report arrives or shutdown begins, each of which wakes every waiting continuation, or until a timeout; it rechecks then, so there is no polling loop. While the program's own track is audible the wait lasts until that track ends, which frees its bank, rechecking at least every ten seconds; once the program has nothing audible, it waits at most `CAPACITY_WAIT_SECONDS` (ten seconds, past the three-second cleanup deadline of the drained track). Only this station's own replacement or cleanup debt can withhold its next slot. Cross-guild priority is removed: each station retains its exclusive pair. A failed lease, a voice error or a next track whose decode fails leads to another attempt, at most three per heard track. When the attempts or the capacity wait are exhausted, or a refill finds or brings nothing more, the station records the reason and the program ends after the heard track drains, or at once if nothing is heard, with no hot loop and no history clearing; `/now` then gives the reason. A continuation whose decode fails is noticed when the callback reaches it, so a gap of silence can precede the next attempt. A pending `/skip` stays requested until its next track is handed to the voice player, so a failed start does not turn it into a natural continuation. At shutdown a waiting continuation returns at once; shutdown still joins every retirement under its existing rules.

`/skip` is registered only with a catalog and requires the caller in the bot's voice channel. It applies while the desired catalog program is the one heard, including while a future generated direction is still being interpreted. It marks a prepared or still-preparing next track as a cut, or asks the continuation task for one and waits up to five seconds for it; it never asks the model itself or queues anything. The current audio keeps playing until the next track is ready, and keeps playing if the next track fails. With no recording left, it says so. During a refill the continuation task returns at once, so the reply says the next recording could not be prepared, and the skip changes nothing and holds no cooldown. A `/play`, `/stop`, `/leave`, a lost voice connection or shutdown removes a prepared next track from the callback and retires it through the same path as any other track; a continuation task for a superseded program, and any late report for a removed track, change nothing.

A program ends `LISTENER_GRACE_SECONDS` (60) after the last listener leaves. A listener is a member in the bot's voice channel who is neither a bot nor deafened (`deaf` or `self_deaf`). With only the Guilds and Voice States intents, disnake's voice states are complete: `GUILD_CREATE` and every `VOICE_STATE_UPDATE` keep `Guild._voice_states`, including both deafened flags. Its member cache is not: without the members intent, members from `GUILD_CREATE` are not cached, and a member is added only by a voice state update while in voice, so `VoiceChannel.members` omits members already in voice when the bot connected. The adapter therefore counts `channel.voice_states`, skips its own user and reads the bot flag from the cached member; an uncached member counts as a listener, so the bot never cuts off a real listener, at the cost of continuing for an unseen bot until that bot changes voice state. The bot registers `on_voice_state_update` and re-evaluates the server on each update, after `/play` and after a `/join` move. With a desired program (playing or preparing) and no listener, it arms one grace period per server, bound to that program; a listener's return or undeafening cancels it, and a further change while armed does not restart it. A newer program cancels it and arms its own if still no listener remains. Every report that can change the desired program also reviews the server again: a failed switch (which can revert a replacement to the heard program), a failed start of ready audio, a drain and a continuation or refill that ends its program. `/stop`, `/leave`, a lost connection and shutdown cancel it through the shared silence path. SobaFM's own voice state leaving the channel also cancels it, because no grace period runs without a connection, and the server is reviewed again when a connection comes back. The timer is an adapter-owned task, so shutdown cancels and joins it, and its sleep is injected so tests control the clock. On expiry it takes the player lock and ends the program only if it is still the registered timer, the same program is desired, the player is connected and current and no listener has returned. If the desired program changed or a listener is present, it reviews the server again instead, so a program that became desired without a review (a failed replacement reverting to the heard program) gets its own grace period. Otherwise it silences through the `/stop` path with the `no_listeners` reason. Its tracks retire through the usual retirements with their original cleanup clocks, failed verdicts and debt, and the bot stays connected.

Every retired, displaced, failed or stopped catalog track keeps its bank and producer task in one retirement task: cancel the bank, cancel and join the producer, then release. The cleanup deadline is three seconds from the bank's first recorded cancellation; a later cancellation does not reset it. A producer that settles after the deadline is a failed cleanup verdict, logged and counted, and the retirement keeps joining it and holds the bank until it settles. A bank that cannot yet be released stays leased in the adapter's debt list. After the generated stop fade, if applicable, `/stop` removes all audio from the callback, reports silence and waits up to five seconds for retirements before replying; ownership continues after that. `/leave` also disconnects. If the voice player cannot start, the claimed track is reported as a failed switch and retired.

SIGTERM and SIGINT set a stop event. From then on `/join` and `/play` are refused, a connection completed during shutdown is dropped, and no new bank is leased. `run` repeatedly disconnects every server and waits for all retirements until none remain, yielding to the event loop on every pass so a finished retirement's bookkeeping callback can run, retries release of retained banks and closes the client. Exit 0 requires all bank leases and voice output credits to be released and all cleanup deadlines to be met.

The adapter logs what was played at INFO, under the requirements' logging rule and never with request text, tokens or interaction data: the recording key and credit snapshot ID when the heard source changes (and when it clears); for each settled retirement, taken before release, the frames handed to the voice player, underruns, `transfer_complete`, `decoder_complete`, `pcm_valid`, `audible_drain`, the bank's `failure`, whether the bank was released and the seconds from its first cancellation to release; voice connected and disconnected; and the shutdown outcome with the leases still held. A silence frame returned while the source's own lock is contended is not attributed to a track.

## Implemented program refill

When the last recording on a program's list starts, the continuation task finds nothing left and starts one `_refill` task, adapter-owned and recorded on the player with its program ([ADR 0011](decisions/0011-program-refill.md)). The task asks the `Matcher` for more, passing the program's history, while the program's refill-budget lock serializes attempts. The player lock stays available for playback and commands during the wait. It takes the player lock only to settle a result, and it discards the result unless the program is still desired, the player is not closing and no shutdown has begun. This check runs again under the lock: voice loss can mark the player closing while the result waits for that lock, before the silence path can stop the program.

A valid list replaces the program's list through `Station.refilled`, and the task schedules the continuation, which prepares the next track as usual and needs no free bank until then. A failed call, a refusal and a list with nothing new each use up one of `MAX_REFILL_ATTEMPTS` (three), with a wait on the injected timer after each, so none can become a hot loop. `refill_wait` takes the wait from `REFILL_WAIT_SECONDS`: 15 seconds and then 60, so three fast failures can outlast a per-minute rate limit. It caps a wait to leave `REFILL_RESERVE_SECONDS` before the heard track ends, which is 16: the last call's 10-second timeout and six seconds of pre-roll. No wait is shorter than 15 seconds, which also applies when nothing is audible or the recording has no listed length. Time left is the catalog's duration minus the frames handed to the voice player. It is only a timing hint: a duration that's too long can leave a gap of silence before the last call, and nothing else depends on it. After the third, `exhausted` records `refill_failed`: the program ends when its heard track drains, or at once if nothing is heard. `NO_RECORDINGS` means every admitted recording has been played or tried, so `exhausted` records `exhausted` with no call made.

`_silence` cancels the task, which covers `/stop`, `/leave`, listener-grace expiry, a lost connection and shutdown, and shutdown joins it with every other owned task. A `/play` cancels it when it accepts a new program. If that replacement then fails and the old program is desired again, `_resume` schedules its continuation, which asks afresh. A brief voice reconnect leaves it running, because that isn't a disconnection. When the task ends it wakes continuations waiting for a bank and reviews the listeners, since the program may have ended. A silent program whose refill is running keeps its own station reservation. It neither delays another server's next track nor lends that server its slots. The refill takes no cooldown claim and gives none back.

## Implemented settings and cooldown

`settings.py` keeps each server's generated duration, volume and change cooldown in SQLite through the standard library, with no ORM or migration framework. `ServerSettings` holds the validated values, with the required defaults and ranges; a generated request fixes its cutoff from the duration at acceptance, including interpretation and pre-roll. A `STRICT` table with `CHECK` constraints repeats the ranges, and `PRAGMA user_version` names the schema, so a file from a newer version is refused rather than changed.

One `SettingsStore` owns the connection and one worker thread. The connection is created on that thread, and SQLite's same-thread check refuses any use from elsewhere, including the event loop. Reads don't wait: `get` returns a validated in-memory copy loaded at startup. `update` validates, then queues one write and awaits it. The worker changes the copy only after the write commits, so a failed write changes nothing, and a caller cancelled mid-write can't leave the copy and the row disagreeing. Writes apply in the order they queued. At most eight wait at once, and at most 1,000 servers have a row, which bounds the copy under the service limit. Writes use SQLite's default rollback journal and full synchronization. Temporary storage stays in memory, because the root filesystem is read-only. `close` refuses new writes, joins queued ones within five seconds, and closes the connection on its thread. `run` calls it after the adapter's shutdown, and a close that fails makes the exit status nonzero.

The adapter sees the store through its `Settings` protocol. `/settings` with no value answers at once from the copy. With values, it defers and awaits the write before anything takes effect. A value out of range, a shutdown or a failed save leaves everything unchanged, and the reply says so. If the acknowledgement fails, nothing is written.

Volume is a linear gain of `volume_percent / 100`. A new connection takes the saved volume. `StationOutput` uses disnake's volume attribute and the locked `audioop-lts` multiplier. It reads the gain after receiving a real source frame. A saved change takes effect at the next frame, even when a database write was delayed. Gains up to 1.0 cannot clip. A gain of 1.0 preserves every sample. At lower gains the product rounds toward negative infinity.

Each station reservation admits at most two voice readers to copy PCM, independently of its bank leases; the process-wide maximum is six. Admission precedes the source read. During pre-roll, backoff or a gap, readers can return the same immutable silence frame with no volume copy. A reader without credit returns that silence without consuming PCM or announcing a switch. A real frame carries its reader's credit until the last reference to the returned bytes is gone, including after disconnect. Disnake holds its previous result while reading the next, so each admitted reader has space for two handed-off frames. If a sink retains both, that reader also returns shared silence until one is released. Shutdown stops further voice reads and observes outstanding credit while disconnect and producer cleanup proceed. A return after the original three-second cutoff counts as a failed cleanup even if the loop observes the return later. The credit remains charged until actual return, and subsequent shutdown calls retain the failed verdict.

Each station's payloads fit its own 524,288-byte PCM scratch partition. A conservative allowance charges two 49,152-byte decoded slices plus 31 frames of 3,840 bytes each. That includes two five-frame mixes (session and program) and one fade-out per reader, one source frame and one volume intermediate per reader, four handed-off frames in total, and the single shared silence frame. The sum is 217,344 bytes per station, within each scratch reservation and the proposed 294,842,368-byte controlled total.

`cooldown.py` holds one server's change cooldown as pure logic: it takes the time and length from its caller and knows nothing of settings or Discord. `/play` and `/skip` take a `Claim` before interpreting a request or selecting a recording, and a refused request calls neither and doesn't extend the wait. A refill isn't a member action and takes none. `/play` validates its text and refuses a second match first, so neither takes a claim. The length is read on every check, so a changed setting applies at once, and the claim's time rather than a stored deadline decides when it ends. The cooldown belongs to the `GuildPlayer`, so it starts afresh when the bot leaves voice or restarts.

A request gives back only its own claim, because `release` compares identity. `/play` gives it back when it ends with no accepted program. `/skip` gives it back unless the reply is that it is skipping. Once accepted, a request's claim stays on `waiting_claim` until its track is offered, then moves to that `Track`. If the callback then reports that track as failed, its claim is given back. A `/skip` still waiting for its next track gives its claim back when its continuation task ends without one, even after the reply has gone. That task leaves the claim alone if a newer program is desired, since the claim is then the newer request's. A late report from an older request, or from a player replaced by a new `/join`, has no effect once a newer claim holds the cooldown. A `/stop` that interrupts a request not yet answered, a `/play` still being matched or a `/skip` still in its wait of up to five seconds for the next track, ends that request with no change, so it gives back its claim. Otherwise `/stop` doesn't give back a claim: the request succeeded, and the cooldown runs on.

`__main__.py` opens the store after reading configuration and before connecting to Discord. It must open, pass validation and commit a real write, in a transaction that also validates every row, so a refused file is left unchanged. Otherwise the service exits 4 ([ADR 0009](decisions/0009-writable-data-volume.md)). Offline tests use real SQLite files for the store and fakes for Discord; they don't establish behavior in the image.

## Implemented voice channel memory

The store keeps each server's voice channel in a second table, `voice_channels`, with its own validated copy and the same worker thread, queue bound and limit of 1,000 servers. A row exists only while a channel is remembered. Schema version 2 adds that table. There is no migration framework: `_open_database` creates any missing table and sets the version in the one transaction that also validates every row, so a version 1 file either upgrades in place with its settings intact or stays exactly as it was. A file newer than the code is still refused.

`/join` checks Connect and Speak, then saves the channel before connecting or moving, so a refusal or a failed save changes nothing at all. If the connection then fails, it restores what was remembered before. `_connect`, which `/join` and a rejoin share, bounds one attempt at `CONNECT_ATTEMPT_SECONDS` (45), because disnake's timeout covers only the handshake and its [UDP discovery](https://github.com/DisnakeDev/disnake/blob/v2.12.2/disnake/gateway.py#L1166) has none. It closes the client of a failed attempt, because disnake does that only for its own handshake timeout, so after anything else the client would stay registered and every later attempt would report "already connected". A move only asks Discord (`move_to` sends the request), so its reply says "Moving to", and if Discord doesn't carry it out the new channel stays remembered while the bot stays put. `/leave` forgets before disconnecting, so a failed save leaves the bot connected with its program playing, and the reply says so. A remembered channel with no connection can still be forgotten. Shutdown disconnects without forgetting, which is what lets the next start rejoin. While a `/join`, `/leave`, rejoin or the forgetting after a loss is under way, a per-server busy mark refuses another `/join` or `/leave`, because their awaits could otherwise interleave and leave the connection and the saved channel disagreeing.

**Telling a disconnection from a reconnect.** `WatchedVoiceClient`, the `disnake.VoiceClient` subclass every connection now uses, reports the difference. SobaFM's own voice state can't: for a transient failure, [`poll_voice_ws`](https://github.com/DisnakeDev/disnake/blob/v2.12.2/disnake/voice_client.py#L506-L512) calls `voice_disconnect` and then `connect` itself, so the state update briefly has no channel while the library recovers. The signal is [`VoiceProtocol.cleanup`](https://github.com/DisnakeDev/disnake/blob/v2.12.2/disnake/voice_client.py#L166-L179), which removes the client from the library's table of live connections. Only [`disconnect`](https://github.com/DisnakeDev/disnake/blob/v2.12.2/disnake/voice_client.py#L522-L541) calls it, and the reconnect path doesn't call `disconnect` unless it gives up. Close codes [4017 and 4021](https://github.com/DisnakeDev/disnake/blob/v2.12.2/disnake/voice_client.py#L463-L467) end the polling loop with no `disconnect` at all, leaving a dead client that still reports connected, so the subclass closes a client whose loop ended and treats that the same way. It also reports when the websocket comes up, so listeners are reviewed after a reconnect, since the state update arrives before the connection is ready. The line references are to the pinned 2.12.2, and a disnake update must recheck them.

**An ended client stays ended,** because it shares one slot per server with whichever client comes next. `disconnect` doesn't stop `poll_voice_ws`, which could otherwise [reconnect](https://github.com/DisnakeDev/disnake/blob/v2.12.2/disnake/voice_client.py#L506-L512), or [time out](https://github.com/DisnakeDev/disnake/blob/v2.12.2/disnake/voice_client.py#L404-L408) and clear the slot, on top of a newer client. So `cleanup` cancels that task. aiohttp's `close` also wakes the loop before `cleanup` has run, so a second `disconnect` could finish last and send the gateway a stale "no channel". So `disconnect` acts once, later callers wait for it, and an ended client does nothing further. If the cancelled loop holds a websocket a reconnect has just opened, it closes it.

**Each voice connection attempt has a deadline.** A stalled attempt could otherwise keep the player waiting indefinitely. UDP discovery has no timeout, and the reconnect path reaches it through `connect` and `potential_reconnect` as well as a first connection. Close code 4015 calls `connect_websocket(resume=True)` directly, and a server answering heartbeats without sending RESUMED could keep that call waiting indefinitely. The subclass bounds all three methods at `CONNECT_ATTEMPT_SECONDS` (45). A resume that times out falls back to the library's normal reconnect path after cleanup. If the failed attempt installed a websocket, the poller takes it out of the shared slot, closes it, and waits for the heartbeat thread that HELLO may have started to exit. It checks the thread every 50 ms so the event loop can finish an outstanding send, even when the service has no spare thread. Repeated cancellation and an explicit disconnect wait for this cleanup to settle. After five failed websockets, [`connect` returns as if it had worked](https://github.com/DisnakeDev/disnake/blob/v2.12.2/disnake/voice_client.py#L376-L392), which also made `/join` reply "Joined", and the loop tries again for ever. So a `connect` that didn't connect gives up for good, which is the disconnection path above. The 45 seconds bound an attempt, not the whole outage: the library's [backoff](https://github.com/DisnakeDev/disnake/blob/v2.12.2/disnake/backoff.py) precedes a normal reconnect and can reach 1,024 seconds on a connection that keeps dropping. A failed resume can therefore take its own 45 seconds, its cleanup, that backoff, and a further bounded reconnect attempt before the connection ends.

While it's down, `_continue` waits instead of starting a track, because `play` [refuses](https://github.com/DisnakeDev/disnake/blob/v2.12.2/disnake/voice_client.py#L636) when not connected and each refusal would use up an attempt and a recording. This matters when the program is silent: a refill's answer, or a freed bank, can arrive during the gap. The wait uses up no attempt or recording, and the bound on waiting for a bank starts again afterwards. `_voice_ready` wakes it when the connection is back, and `_lose_voice` wakes it to stand down if it isn't. An explicit `_disconnect`, including `/leave` or a fresh `/join` during the gap, also wakes it as soon as the player is marked closing. A silent server has priority for a free bank only while its voice is connected: a reconnect cannot keep a healthy server's next track waiting for a bank it cannot yet use. Existing leases remain charged throughout the gap.

The subclass also keeps the player thread from being lost. `AudioPlayer.stop` doesn't wake a thread [waiting on a connection that's down](https://github.com/DisnakeDev/disnake/blob/v2.12.2/disnake/player.py), which would hold one of the 64 tasks until a restart, so `cleanup` sets the event it waits on. The thread reads one more frame and then sees it has ended, and `is_connected` stays false. A voice server update while still connected [clears the endpoint](https://github.com/DisnakeDev/disnake/blob/v2.12.2/disnake/voice_client.py#L310) until the reconnect finishes, and `sendto` would then raise and end the thread, with no restart until the next track. So `send_audio_packet` drops the frame instead, including when the loop does this during the encode, which releases the GIL. Any other error in that thread still ends it until the next track.

A real disconnection ends the program through `_silence`, removes the player and forgets the channel. Every track retires through the usual `_retire` with its original cleanup clock, failed verdict and retained debt, and the adapter owns the work as a task, so shutdown joins it. `_silence` also cancels a refill. While that work waits for the player lock, the player is marked as closing: `_resume`, `_continue` and `_refill` start nothing for it, a `/play` that finishes matching then replies that playback stopped, and it has no priority for a bank in `_bank_free`. The adapter's own disconnects mark the player the same way first, so their `cleanup` isn't a loss, and a report during shutdown forgets nothing. `_disconnect` runs once per player and doesn't call `disconnect` again on a client the library already closed. A kick that arrives after a forced close waits for the library's own timeout, which `/join` and rejoin now set to 20 seconds rather than its default of 60.

**A new gateway session** empties the library's table without `cleanup`, because `parse_ready` calls [`clear`](https://github.com/DisnakeDev/disnake/blob/v2.12.2/disnake/state.py). A live client's next reconnect then can't hear its updates and gives up within the timeout, so it ends like any disconnection: the program ends and the channel is forgotten, on every affected server. Rejoining runs once per process, so it doesn't bring them back. The requirements' "on disconnection, forget the channel" covers this, and [operations](operations.md#voice-channel-memory) tells operators to expect it.

A deleted channel, seen through `on_guild_channel_delete`, ends its connection at once without waiting for the library. If it was only remembered, it is forgotten. A move is seen as SobaFM's own voice state naming a channel other than the remembered one: the adapter saves it, keeps the same player, program and tracks, and reviews listeners. Current audio carries on from where it was, because disnake's player thread waits while the connection is down and reads no frames during the gap ([`AudioPlayer._do_run`](https://github.com/DisnakeDev/disnake/blob/v2.12.2/disnake/player.py)). A failed save there is logged and retried at the next state update.

The first `on_ready` starts one rejoin task, once per process, so a later ready event or a gateway resume starts nothing. Up to `MAX_CONCURRENT_REJOINS` (4) workers take servers from the remembered list. Each checks that the server, channel and voice channel type exist and that `permissions_for(guild.me)` allows Connect and Speak, then connects within `REJOIN_ATTEMPTS` (2) attempts through `_connect`. Anything ineligible is forgotten with a safe reason. A server reported unavailable has no answer yet, so its channel stays for the next start. So does a `RuntimeError` from a connection attempt, such as no task left for a voice keep-alive thread, which says something about this host and nothing about the channel. A rejoined server gets an ordinary idle player: no program, no bank and no voice player until someone uses `/play`. Shutdown cancels the rejoin task, and closing the bot ends any connection still in progress.

Tests run disnake's real `VoiceClient` state machine against a scripted gateway and websocket for the reconnect, kick, move and abandoned-close cases, because the signal is a fact about that code. They don't establish behavior on real Discord, and which close codes Discord actually sends for each case is the library's reading, not something measured here.

Configuration comes from environment variables (see `.env.example`). `SOBAFM_DISCORD_TOKEN` is required and is removed from the process environment when read, so child processes cannot inherit it; it is excluded from the configuration's representation, and configuration and client errors are logged without values or messages. `SOBAFM_CATALOG` and `SOBAFM_REVIEWS` must be set together; without them `/play` and `/skip` are not registered and a safe warning is logged. With them `SOBAFM_GEMINI_API_KEY` is required. It is removed from the environment in the same way, used for Gemini interpretation and sent only as a request header. An optional `SOBAFM_LYRIA_API_KEY` enables generation alongside the Gemini key, independently of catalog configuration. Both keys are removed from the environment when read. `run` closes the shared Gemini client after the adapter shuts down. Each source's state, provided count and admitted count are logged at startup. The entry point below reads this configuration and supplies the decoder-backed producer. Offline tests use faked disnake objects and make no token, gateway or voice contact; they do not establish voice behavior, timing or DAVE negotiation.

## Implemented entry point and deployment

`python -m sobafm` (`__main__.py`) runs in a fixed order. First, when the file runs as the program and before its native dependencies are imported, `crash_dumps.py` writes 0 to `/proc/self/coredump_filter` and then sets `PR_SET_DUMPABLE` to 0. The credentials are in the process's initial environment from the moment it starts, and a crash would otherwise copy its memory into the working directory, the writable `/data`, or to the host's crash handler. Both controls are read back, and if either didn't take effect the service refuses to start (exit 5). The order matters, because a non-dumpable process's `/proc` files become root-owned. A crash of the main process then leaves no dump to debug. Importing the module, as the tests do, applies neither. Then a limit gate reads the cgroup v2 `memory.max`, `memory.swap.max` and `pids.max` that the process sees at `/sys/fs/cgroup` and refuses to start (exit 3) unless they are exactly ADR 0012's candidate 268435456, 0 and 64. A missing, unreadable or different value refuses before any configuration, catalog, media, Discord or audio input is read. Then the adapter's `Config` reads the token, configured provider keys, catalog snapshot and reviews from the environment, `SOBAFM_DATABASE` names the settings database, and `SOBAFM_MEDIA` names the media manifest, required exactly when a catalog is configured. A configuration error exits 2 without values. The settings database is then opened, and a refusal exits 4 with a safe kind. Finally the adapter's `run` starts the bot with a `MediaProducer` and the store, and handles SIGTERM through the adapter's shutdown.

The catalog snapshot has no audio location, so `media.py` reads a separate bounded operator manifest (at most 256,000 bytes and 1,000 entries, duplicate keys rejected). Each entry binds a recording key to a file relative to the manifest's directory that may not leave it, its exact size and SHA-256, and `max_pcm_bytes`, a whole number of frames up to four hours of PCM that becomes the decode's overrun bound. `MediaProducer` is the adapter's `Producer`: for each track it creates one `DecodeProducer` on the adapter's already-leased bank and runs start, finish and settlement on a worker thread. On cancellation it cancels the decode, keeps awaiting the worker through repeated cancellation, and raises only after the decoder process, its threads and descriptors have actually settled. A failed decode is logged by its failure kind and leaves the bank stopped, so the callback reports a failed switch and current audio continues. The adapter's retirement keeps the single lease, the original three-second clock from the bank's first cancellation, the failed-verdict count and retained debt unchanged.

The `Dockerfile` builds the locked runtime dependencies with uv 0.13.6 on the reviewed Python 3.14 base pinned by digest, then installs the reviewed mpg123 1.33.7 package set with its exact stable dependencies, including libopus, and runs as UID 1000. It contains no FFmpeg. `compose.yaml` defines one service with init, a read-only root, all capabilities dropped, no new privileges, memory and memory-plus-swap 268,435,456 bytes, 64 tasks, two CPUs, `on-failure:5`, a read-only `./catalog:/catalog` bind mount, a writable named `sobafm-data` volume at `/data` for the settings database ([ADR 0009](decisions/0009-writable-data-volume.md)) and two 1 MB log files. A new named volume takes the ownership of the image's `/data`, UID 1000. Offline tests check the gate against a fake cgroup root, configuration, the producer with a Python child in place of mpg123, and the deployment files statically. Historical builds, volume checks and decoder checks are recorded in the [deployment evidence assessment](https://github.com/slackysoba/sobafm/issues/167#issuecomment-6790829606), each bound to its original source and target. They do not qualify current-main fit, decoder behavior, persistent restart during playback or Discord behavior; fresh source-only build availability also remains unverified.

## Generated playback

`lyria.py` carries Lyria RealTime audio into the PCM banks under [ADR 0008](decisions/0008-lyria-realtime-path.md), recording the maintainer's free-tier choice for this non-commercial community project. Free-tier model availability remains unknown and no successful live call is recorded. [#165](https://github.com/slackysoba/sobafm/issues/165) prepares a separately authorized check, without approving execution or spend. The command uses this transport. Offline integration tests use loopback peers.

`LyriaSession` owns one WebSocket feeding one bank, over the existing `aiohttp`. It sends the setup and waits for `setupComplete`, then sends the prompts, config and `PLAY`. `parse_message` validates each whole message before anything is committed: the base64 is found and checked in place, and only the rest is parsed as JSON, so a message is written whole or not at all. Reading is paused between messages and a message is taken only when the bank has room for all of it, so a full bank applies back-pressure and never counts as a stall. Messages are limited to under 524,288 bytes, one socket read to 65,536 and staged TLS ciphertext to about 98 KiB. ADR 0008 maps each session's copies onto its lease; ADR 0012 provides three exclusive station pairs and a 294,842,368-byte controlled total. Assembling WebSocket fragments and folding over 2,048 socket reads of one frame can each briefly need a third copy. Both use a station's reserved 524,288-byte drain capacity inside a synchronous reader call. The temporaries are released before another operation can use the reservation. Closing drops the connection without reading, leaving that reservation available during simultaneous stops.

A session ends as `rejected`, `connect`, `prepare_timeout` (no six seconds of audio within 15), `stalled` (no audio for five seconds with room in the bank), `truncated`, `closed`, `oversized`, `malformed`, `filtered` or a clean close. Handshake failures report `access_denied` for HTTP 401 or 403, `rate_limited` for 429 and `service_error` for 5xx. A WebSocket 1011 also reports `service_error`. The latter two retry on the same schedule as 408 (`connect`). Access denial, other rejected handshakes and policy closes remain terminal. After readiness it declares the end of PCM so buffered audio drains, because everything committed was validated. Before readiness it stops the bank, so nothing short is ever audible. WebSocket autoclose is disabled so even a peer close without a status reaches the pump directly. Every stopped session drops its connection without a close handshake, even before its owner calls `finish`. `cancel` and `finish` follow `DecodeProducer`: one deadline, three seconds from the first of cancellation, failure or end, that repetition doesn't move; two seconds in, pending cleanup is interrupted without abandoning the joined close owner; and settling after the deadline is an `expired` verdict that never changes. A done callback records settlement even when the pump was cancelled before its first step. The owner keeps the lease until `settle` returns.

`GeneratedStream` keeps one program playing across sessions. It renews after 540 seconds or when a session ends, pre-rolls the replacement on the station's second bank and crossfades over four seconds, or over what is left of the old audio. `read_frame` has the same contract as `PcmBank.read_frame` and never waits. It mixes with linear gains in the voice callback using about six frames of prepaid scratch, and `fade_out` ramps to silence over two seconds. Each renewal gets three attempts. The supervisor checks for a terminal refusal from the audible session before each attempt, including after backoff. At a crossfade handoff with a refusal from the retiring feed, it stops the surviving producer, preserves the refusal, and lets the remaining admitted PCM drain to EOF while the session owns its close. A planned renewal that fails leaves a healthy session playing. Three short sessions in a row end the stream. Without a second bank, the session plays out, its bank is returned and the next follows after a gap. Every retiring session keeps its lease in its own retirement task until it has actually settled, and `finish` reports failed cleanups and any bank still retained. Returning a feed’s bank wakes the adapter’s capacity waiters even while the renewed stream continues. A bank retained as cleanup debt wakes waiters only when its release succeeds.

The station accepts a validated generated plan while the currently heard source keeps playing. It leases the first bank before starting a stream or voice playback, as it does for a catalog producer. The stream takes ownership of that lease and admits any retry or renewal through the same station reservation. A declined interpretation leaves even an unheard catalog continuation intact. One generated interpretation can be in flight per server. A catalog request supersedes that interpretation when its match commits successfully. A refusal, failed match or failed admission leaves the generated request on its original clock. A new generated direction opens a fresh session, so BPM and scale changes take effect from setup. A generated-to-generated replacement mixes four seconds of frames from the two leased banks with the same linear gains as renewal. Boundaries involving catalog audio switch successively. The callback checks each generated input’s original monotonic cutoff, including a fading predecessor. An owned timer also removes the expired program when voice has stopped reading.

If expiry clears its own outstanding switch before the callback report arrives, the station checks the detached track’s frame count. An emitted generated frame displaces the earlier catalog credits. With zero generated frames, the earlier catalog track can keep playing. Whichever path settles the switch starts the exact ready replacement. If both banks are leased, the accepted replacement waits outside the player lock with a ten-second capacity deadline. During voice recovery it keeps its ready audio and cooldown claim without leasing a bank. A bank return, voice readiness, terminal loss, stop or supersession wakes the waiter. Under the lock it checks the exact audio, claim and connection before starting. Waking leaves the original capacity deadline in place. If voice is ready and capacity is still exhausted at the deadline, it returns its own claim.

The event loop observes terminal pre-roll failure independently of the voice callback. It preserves the provider reason through a simultaneous cutoff and releases only that unplayed track’s cooldown claim. The watcher and voice callback each settle a failure only if they own the live switch. Once an audible feed drains during recovery, `/now` gives the remaining duration and shows recovery until a replacement frame is handed to voice. A stop fades generated audio for up to two seconds and then detaches it even if voice stalled. Disconnect and shutdown detach it immediately.

Each session observes cleanup from its first stop, independently of how long admitted PCM takes to drain. The adapter records an expired verdict at the original three-second deadline. The stream owns each lease through settlement, and the adapter retains the stream through finish and any remaining debt. Tests use the real aiohttp client on loopback, including TLS. Free-tier access, Discord continuity, listening quality and image qualification remain open. See [provider access and free-tier limits](provider-access.md).

## Decisions to establish first

The [accepted decoder-PTY amendment](decisions/0003-decoder-pty-exclusion.md)
excludes only kernel PTY backing alongside kernel pipe/socket storage. It kept
the stock decoder and historical 98,979,840-byte total. ADR 0012 proposes new
explicit station partitions and totals while preserving this exclusion. A
subsequent pair requires actual userspace/process/FD settlement and all other
admission gates; prior excluded kernel objects may remain unreclaimed, with no
physical/kernel backlog bound. Original cancellation clocks and userspace debt
remain. This contract amendment does not qualify runtime fit or adopt the
proposed application architecture.

- Source-specific acquisition/storage implementations for Jamendo and Free Music Archive, with complete recording credits and access evidence. [ccMixter is not an enabled audio source](requirements.md#first-source-evaluation).
- The simplest viable non-root Docker resource model under the approved capacity definition: accepted for amd64 in [ADR 0004](decisions/0004-amd64-whole-service-adoption.md); application qualification remains open and native arm64 is on hold ([#60](https://github.com/slackysoba/sobafm/issues/60)).
- Supported dependencies and decoder distribution without a bespoke supply system by default. The Discord voice library is selected and locked: disnake with DAVE through dave.py ([ADR 0005](decisions/0005-discord-voice-library.md)). `discord_adapter.py` uses it. The decoder distribution remains open.
